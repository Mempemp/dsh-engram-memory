# dsh-engram-bridge

**Память engram ведётся сама и приходит в ход сама.** Плагин DeepSeek Harness закрывает три вещи, без которых память остаётся «инструментом, про который надо помнить»:

1. **правила живут в системном промпте** (`ctx.systemPrompt.section`) — модель знает про память без напоминаний;
2. **поиск** — на `agent/pre-step` последнее сообщение пользователя превращается в запрос по базе, до двух записей в жёстком бюджете встают в ход;
3. **запись** — плагин сам разбирает законченный ход (запрос, изменённые файлы, команды, итог) и сохраняет его в engram через CLI, без модели, без LLM и без ключей.

Инструменты engram остаются: там pull-путь (модель сохраняет и ищет явно), здесь push-путь с обеих сторон. Стор один — `engram.db`: читается **только на чтение**, пишет по-прежнему engram.

## Уровни памяти

| `scope` | что там | видно |
| --- | --- | --- |
| `project` (по умолчанию) | устройство воркспейса, принятые решения, грабли | только в своём проекте |
| `personal` | о пользователе и его предпочтениях | в любом проекте, с пометкой `·общее` |
| `global` | конвенции, действующие везде (оформление, стиль, запреты) | в любом проекте, с пометкой `·общее` |

Общий слой держит одно место из двух в бюджете инъекции: если подходящая общая запись есть, она попадёт в ход даже когда по рангу её обходят проектные. Автосохранение всегда пишет `project` — в общий слой попадает только то, что модель или пользователь назвал правилом.

## Чего в плагине нет

- нет своего процесса, порта, демона и сети;
- нет ключей и моделей: поиск лексический (FTS5/BM25 внутри engram), запись — детерминированный разбор хода;
- нет нативных модулей — используется `node:sqlite` самого рантайма;
- нет токенов в простое: нет совпадений — нет инъекции.

## Установка

```
dsh plugin --profile web add <путь-или-URL>
```

Из бандла 1С плагин приезжает строкой каталога (`kind: plugin`) вместе с MCP-сервером engram.

## Настройка

Всё необязательное. Значения берутся из того же файла, что читает шим MCP-сервера, — `%LOCALAPPDATA%\DSH-1C\engram-mcp.json` (путь переопределяется `ENGRAM_MCP_CONFIG`):

```json
{ "dataDir": "D:/engram-data", "project": "my-project", "capture": true }
```

| ключ | по умолчанию | смысл |
| --- | --- | --- |
| `enabled` | `true` | выключить плагин целиком |
| `budget` | `1200` | бюджет инъекции в символах |
| `topK` | `2` | сколько записей максимум |
| `dataDir` | `%USERPROFILE%\.engram` | где лежит `engram.db` |
| `project` | `.engram/config.json` в рабочем каталоге, иначе имя каталога | проект записи в базе |
| `capture` | `true` | автосохранение законченного хода |
| `captureRequireChange` | `false` | `true` — сохранять только ходы, где были изменены файлы или выполнены команды |
| `captureResearch` | `true` | считать исследовательский ход (чтения, поиск) достаточным основанием для записи |
| `captureReadMin` | `3` | сколько чтений/поисков делают ход исследовательским |
| `captureMinChars` | `200` | короче этого итог хода не сохраняется |
| `captureMaxChars` | `2000` | предел тела записи |
| `captureType` | `discovery` | тип записи engram |
| `engramPath` | поиск в `$DSH_HOME/mcp/engram/package` | бинарник engram для автосохранения |

## Как строится запрос

- запрос — последнее сообщение пользователя; слова от трёх знаков, стоп-слова выброшены;
- каждое слово ищется префиксом (`диариз*` находит «Диаризация»), а длинные — ещё и усечёнными на два знака (`диаризации` → `диаризаци*`): морфологии в engram нет, и это ловит падежи;
- порядок — BM25; мягко удалённые записи и записи чужого проекта отбрасываются;
- запись, уже показанная в этой сессии, не повторяется;
- запись, не влезающая в бюджет, отбрасывается целиком, а не обрезается: обрубок стоит токенов и не приносит ответа.

## Что попадает в автосохранение

Разбирается **законченный ход** — момент `turn/end`, когда ход уже собран целиком: реплика пользователя, вызовы инструментов, итоговый текст. Запись строится, если итог содержательнее `captureMinChars` **и** ход что-то сделал или что-то выяснил:

- **сделал** — менял файлы или выполнял команды; в записи появляются `Файлы:` и `Команды:`;
- **выяснил** — прочитал и просмотрел не меньше `captureReadMin` мест (`read`, `glob`, `grep`, веб-поиск) — разбор проекта потом экономит работу не меньше правки; в записи появляется `Прочитано:`.

Ход без изменений и без чтения (разговор, объяснение на словах) не записывается. `captureRequireChange: true` оставляет только работу с изменениями, `captureResearch: false` — только изменения.

Заголовок берётся из первой содержательной строки итога: междометия («Привет!», «Ок», «Готово»), markdown-акценты и приветствие в начале строки отбрасываются — заголовок уходит в инъекцию и должен читаться как имя работы. Короткая строка годится, если несёт конкретику: «Фикс 413», «Диаризация: выбор». Тема записи (`--topic` = проект + слаг заголовка) делает работу идемпотентной: engram **обновляет** запись о той же работе, а не плодит дубли. Работа запоминается один раз за сессию.

Тот же разбор повторяется страховочно на `agent/pre-step` — если событие `turn/end` по какой-то причине не пришло, работа всё равно попадёт в память со следующим вопросом. Двойной записи при этом не бывает: тема, уже записанная в этой сессии, второй раз не отправляется вовсе (сравнение по `--topic`, без окна времени), а если запись всё-таки придёт дважды из разных сессий, engram обновит существующую строку, а не создаст вторую — проверено: три записи с одной темой дают одну строку при `revision_count: 3`.

## Границы

- `node:sqlite` в Node 22/24 помечен экспериментальным и печатает `ExperimentalWarning` в лог — поведение от версии к версии не обещано;
- субагенты инъекцию не получают намеренно: у них своя задача и свой контекст;
- проект определяется по рабочему каталогу хода, поэтому запись, сохранённая из другого каталога, найдётся только при совпадении имени проекта;
- автосохранение пишет через CLI engram: если бинарник не найден, оно один раз сообщает об этом в лог и выключается, ход не ломается;
- автосохранение ставит CLI те же переменные, что и шим MCP: свой каталог данных и `ENGRAM_NO_UPDATE_CHECK=1` — иначе каждый запуск бинарника стучит в GitHub за версией;
- правила живут в секции системного промпта, поэтому плагин объявляет `inject: ['systemPrompt']`: без этого объявления `ctx.systemPrompt` не существует, секция не регистрируется, и ошибки тоже нет — правила просто молча не доезжают.

## Проверка

```
node test/store.smoke.mjs    # поиск, бюджет, промахи
node test/hook.smoke.mjs     # pre-step, общий слой, автосохранение, отказы
node test/capture.smoke.mjs   # разбор хода: когда запись нужна, а когда нет
```

`store` прогоняет 19 запросов (точная форма, падежи, словообразование, множественное число, синонимы, идентификаторы, регистр) на 10 записях — recall@1 19/19 и на синтетической базе со схемой engram, и на настоящей базе, собранной CLI engram v2.0.0, ~0,3 мс на запрос. `hook` проверяет инъекцию и запись на поддельном `ctx`: сообщение встаёт перед репликой пользователя, повтор не инжектится, общая запись получает место в бюджете, чужой проект не утекает, автосохранение доходит до базы через настоящий engram, без базы ход не меняется, `dispose` освобождает стор. `capture` — разбор хода: без работы и с коротким итогом записи нет, с изменённым файлом и содержательным итогом есть, тело режется по бюджету.

Если рядом нет бинарника engram, эти проверки пропускаются — задайте `ENGRAM_BINARY`.
