# dsh-engram-memory

**Память engram ведётся сама и приходит в ход сама.** Плагин DeepSeek Harness закрывает три
вещи, без которых память остаётся «инструментом, про который надо помнить»:

1. **правила живут в системном промпте** (`ctx.systemPrompt.section`) — модель знает про
   память без напоминаний, знает про общий слой и как поднять туда проектное правило;
2. **поиск** — на `agent/pre-step` последнее сообщение пользователя превращается в запрос по
   базе, до двух записей в жёстком бюджете встают в ход;
3. **запись** — плагин сам разбирает законченный ход (запрос, изменённые файлы, команды,
   прочитанное, итог) и сохраняет его в engram через CLI, без модели, без LLM и без ключей.

Инструменты engram остаются: там pull-путь (модель сохраняет и ищет явно), здесь push-путь с
обеих сторон. Стор один — `engram.db`: читается **только на чтение**, пишет по-прежнему engram.

Пакет **самодостаточен**: MCP-сервер engram (бинарь + шим) лежит внутри пакета, плагин сам
раскладывает его в харнесс и сам объявляет сервер. Внешних ключей, аккаунтов и сети для работы
памяти не нужно.

Схема целиком — [`docs/architecture.html`](docs/architecture.html).

## Уровни памяти

| `scope` | что там | видно |
| --- | --- | --- |
| `project` (по умолчанию) | устройство воркспейса, принятые решения, грабли | только в своём проекте |
| `personal` | о пользователе и его предпочтениях | в любом проекте, с пометкой `·общее` |
| `global` | конвенции, действующие везде (оформление, стиль, запреты) | в любом проекте, с пометкой `·общее` |

Общий слой держит одно место из двух в бюджете инъекции: если подходящая общая запись есть, она
попадёт в ход даже когда по рангу её обходят проектные. Автосохранение всегда пишет `project` —
общий слой наполняет модель по правилам: правило, всплывшее в проекте, сохраняется в проект, а
поднимается в `global` через `mem_update`, когда пригодилось второй раз.

## Чего в плагине нет

- нет своего процесса, порта, демона и сети;
- нет ключей и моделей: поиск лексический (FTS5/BM25 внутри engram), запись — детерминированный разбор хода;
- нет нативных модулей — используется `node:sqlite` самого рантайма;
- нет токенов в простое: нет совпадений — нет инъекции.

## Установка

```bash
npm pack
node D:/DSH/local-plugins/dsh-desktop-install.mjs dsh-engram-memory-1.0.0.tgz dsh-engram-memory
```

Затем перезапуск десктопа. При старте плагин сам, идемпотентно:

1. кладёт свою MCP-половину в `<harness>/mcp/engram/package`, если версия копии отличается
   (занятый бинарник — не ошибка: обновится при следующем спокойном запуске);
2. добавляет запись сервера `engram` в `<harness>/dsh-mcp.json`, если её там нет: настройку
   человека не переписывает, перед правкой делает бэкап `dsh-mcp.json.bak-<метка>`.

Оба шага выключаются настройкой `registerMcp: false`. Из бандла 1С плагин приезжает строкой
каталога вместе с той же MCP-половиной.

## Настройка

Всё необязательное. Настройки читаются из того же файла, что читает шим MCP-сервера, —
`%LOCALAPPDATA%\DSH-1C\engram-mcp.json` (путь переопределяется `ENGRAM_MCP_CONFIG`):

```json
{ "dataDir": "D:/engram-data", "project": "my-project", "capture": true }
```

| ключ | по умолчанию | смысл |
| --- | --- | --- |
| `enabled` | `true` | выключить плагин целиком |
| `budget` | `1200` | бюджет инъекции в символах |
| `topK` | `2` | сколько записей максимум |
| `dataDir` | `%USERPROFILE%\.engram` | где лежит `engram.db` |
| `project` | `.engram/config.json` в рабочем каталоге, иначе имя каталога | проект записи в базе |
| `capture` | `true` | автосохранение законченного хода |
| `captureRequireChange` | `false` | `true` — сохранять только ходы, где были изменены файлы или выполнены команды |
| `captureResearch` | `true` | считать исследовательский ход (чтения, поиск) достаточным основанием для записи |
| `captureReadMin` | `3` | сколько чтений/поисков делают ход исследовательским |
| `captureMinChars` | `200` | короче этого итог хода не сохраняется |
| `captureMaxChars` | `2000` | предел тела записи |
| `captureListChars` | `600` | бюджет списков (`Файлы`/`Команды`/`Прочитано`) внутри тела; остальное достаётся итогу |
| `captureTitleChars` | `200` | предел заголовка заметки: по нему запись узнают в поиске и в подаче |
| `hygieneAfterDays` | `30` | сколько дней заметка должна отлежаться усвоенной, прежде чем её можно убрать из обращения |
| `captureType` | `discovery` | тип записи engram (на обработку не влияет: сырой считается любая запись, кроме карточек) |
| `engramPath` | бинарь из пакета | свой бинарник engram для автосохранения |
| `consolidateHint` | `true` | подсказывать модели, что тему пора сжать в один вывод |
| `consolidateMinRevisions` | `3` | сколько раз должна обновиться запись, чтобы подсказка появилась |
| `consolidate` | `true` | объявлять ли команду обобщения `/memory-consolidate` |
| `consolidateNotes` | `20` | сколько сырых заметок берём за один проход |
| `consolidateInputChars` | `12000` | предел подборки заметок по знакам |
| `consolidateNoteChars` | `1400` | сколько знаков одной заметки видит модель на проходе (запрос и ключи целиком, проза — началом и концом) |
| `consolidateMaxPasses` | `3` | сколько проходов делает одно нажатие (предохранитель по цене) |
| `consolidateTimeoutMs` | `300000` | сколько ждём ответа модели (проход можно отменить) |
| `consolidateType` | `pattern` | тип записи для карточки-вывода |
| `consolidateProvider` | пусто | явный провайдер для обработки (иначе — модель по умолчанию) |
| `consolidateModel` | пусто | явная модель для обработки |
| `registerMcp` | `true` | раскладывать MCP-половину и объявлять сервер |
| `harnessDir` | `%APPDATA%\dsh-desktop\harness` | каталог харнесса десктопа |
| `nodePath` | узел из установки десктопа | узел для запуска шима MCP |

Каталог данных, проект и профиль инструментов MCP-сервера задаются тем же файлом
(`dataDir`, `project`, `timezone`, `tools`) — его читает и шим, и плагин, поэтому запись и
поиск смотрят в одну базу.

## Как строится запрос

- запрос — последнее сообщение пользователя; слова от трёх знаков, стоп-слова выброшены;
- каждое слово ищется префиксом (`диариз*` находит «Диаризация»), а длинные — ещё и усечёнными
  на два знака (`диаризации` → `диаризаци*`): морфологии в engram нет, и это ловит падежи;
- порядок — BM25; мягко удалённые записи и записи чужого проекта отбрасываются;
- запись, уже показанная в этой сессии, не повторяется;
- запись, не влезающая в бюджет, отбрасывается целиком, а не обрезается: обрубок стоит токенов
  и не приносит ответа.

## Что попадает в автосохранение

Разбирается **законченный ход** — момент `turn/end`, когда ход уже собран целиком: реплика
пользователя, вызовы инструментов, итоговый текст. Запись строится, если итог содержательнее
`captureMinChars` **и** ход что-то сделал или что-то выяснил:

- **сделал** — менял файлы или выполнял команды; в записи появляются `Файлы:` и `Команды:`;
- **выяснил** — прочитал и просмотрел не меньше `captureReadMin` мест (`read`, `glob`, `grep`,
  веб-поиск) — разбор проекта потом экономит работу не меньше правки; в записи появляется `Прочитано:`.

Ход без изменений и без чтения (разговор, объяснение на словах) не записывается.
`captureRequireChange: true` оставляет только работу с изменениями, `captureResearch: false` —
только изменения.

Заголовок берётся из первой содержательной строки итога: междометия («Привет!», «Ок»,
«Готово»), markdown-акценты и приветствие в начале строки отбрасываются — заголовок уходит в
инъекцию и должен читаться как имя работы. Короткая строка годится, если несёт конкретику:
«Фикс 413», «Диаризация: выбор». Тема записи (`--topic` = проект + слаг заголовка) делает работу
идемпотентной: engram **обновляет** запись о той же работе, а не плодит дубли. Работа
запоминается один раз за сессию.

Тело записи — `Запрос` + `Итог` + списки, и бюджет делится осознанно: спискам (`captureListChars`,
600 знаков) свой, остальное достаётся итогу. Итог — это проза модели, её всегда можно перечитать в
истории; пути и команды — машинный факт, который заново не выдумать. Поэтому при длинном итоге
первым режется он: раньше бюджет выбирал итог, а списки за ним не помещались и пропадали целиком.
Хотя бы один путь в записи остаётся всегда: слишком длинный путь режется сам, но не выбрасывается.

Предел знаков — **верхняя граница, а не цель**. В заметке остаются начало ответа (о чём речь) и
**вывод — последние абзацы целиком**, а середина заменяется пометкой `…пропущено N знаков…`. Так
решает не размер, а структура: вывод живёт в конце ответа, и раньше именно он терялся первым, а
сохранялось вступление. Если бюджета не хватает, короче становится начало, а вывод остаётся целым.
Внутри куска текст режется по ближайшей границе — абзац, строка, конец предложения, конец слова, и
лишь в крайнем случае по символу; заголовок укорачивается тем же правилом (целое предложение, если
оно влезает в `captureTitleChars`, иначе до конца слова). Поэтому длина записи плавает: она короче
предела, зато последняя фраза в ней целая, а «…» посреди слова не встречается.

Почему середина не хранится: модели читают начало и конец текста, а середину длинного контекста не
читают вовсе ([Lost in the Middle, Liu et al., 2023](https://arxiv.org/abs/2307.03172)). Держать её
целиком — платить за то, что всё равно не будет прочитано; пометка при этом честно говорит, что
кусок был.

**Цена обобщения не зависит от длины ответов.** В проход заметка уходит срезом (`consolidateNoteChars`,
1400 знаков): `Запрос` и ключи — целиком, проза — началом и концом. Заметка от хода с ответом на 6 000
знаков и заметка на 900 знаков читаются моделью одинаково, поэтому проход всегда стоит примерно
одинаково, а не растёт вместе с длиной ответов.

Тот же разбор повторяется страховочно на `agent/pre-step` — если событие `turn/end` по какой-то
причине не пришло, работа всё равно попадёт в память со следующим вопросом. Двойной записи при
этом не бывает: тема, уже записанная в этой сессии, второй раз не отправляется вовсе (сравнение
по `--topic`, без окна времени), а если запись всё-таки придёт дважды из разных сессий, engram
обновит существующую строку, а не создаст вторую — проверено: три записи с одной темой дают одну
строку при `revision_count: 3`.

## Обобщение: хроника и вывод

Автосохранение пишет **хронику** — что делали в этом ходе. Семантику памяти держат **выводы**,
и их формулирует модель: заметка говорит «правили разбор хода», вывод — «у нас один разбор хода
на `turn/end`, потому что pre-step видит только прошлый ход».

Правила говорят модели об этом прямо: закончив работу, сохранить вывод одной записью
(структура `What`, `Why`, `Where`, `Learned`; тип `pattern`, `decision` или `architecture`),
а не добавлять ещё одну заметку в хронику. Плюс плагин подсказывает момент: если запись по
текущей теме обновлялась `consolidateMinRevisions` раз и больше, в инъекцию добавляется строка
вида

```
- [6] эту тему обновляли 4 раза: если работа закончена, сохрани вывод одной записью
  (`mem_save` с тем же `topic_key`, тип `pattern`) вместо новой заметки.
```

Подсказка встаёт только в бюджет инъекции и выключается `consolidateHint: false`. Так работает
гибрид: дешёвая детерминированная хроника с обеих сторон + дорогое обобщение там, где модель и
так думает о работе.

Как это делают другие (для сверки подходов):

- **Letta / MemGPT 2.0, sleep-time compute** ([paper](https://arxiv.org/abs/2504.13171),
  [blog](https://www.letta.com/blog/sleep-time-compute)) — рядом с основным агентом живёт
  «спящий», у которого есть права на правку памяти; он асинхронно переписывает память в чистое
  и сжатое состояние, потому что инкрементальная запись со временем становится беспорядочной;
- **LangMem** ([guide](https://langchain-ai.github.io/langmem/guides/extract_semantic_memories/)) —
  два режима: инструменты в горячем пути разговора и фоновый менеджер памяти, который извлекает и
  консолидирует после хода;
- **Mem0** ([paper](https://arxiv.org/html/2504.19413v1)) — извлечение фактов моделью и решение
  ADD/UPDATE/DELETE/NOOP против похожих записей; в апреле 2026 апстрим упростил схему до
  ADD-only — накапливать и не перезаписывать ([repo](https://github.com/mem0ai/mem0));
- **Generative Agents** — периодическая «рефлексия»: синтез выводов из сырых наблюдений с оценкой
  важности, чтобы высокоуровневое знание приходило на смену потоку событий.

Что из этого нам по силам дальше и что нет: фоновый проход обобщения (как «спящий агент» Letta) уже
есть — плагин зовёт модель харнесса без единого внешнего ключа (так делает memOs), а бюджет, таймаут,
отмена и отчёт у него свои; см. «Обработка заметок». Запускает его человек — кнопкой или командой,
потому что это стоит токенов вне разговора. Не сделано пока одно: расписание (крон вместо нажатия).



## Обработка заметок

Основной путь — вкладка **«Память Engram»** в настройках DSH. На ней:

- очередь: сколько заметок ещё не сведено в выводы и полоска по ним. Обработанной считается заметка, на
  которую ссылается хотя бы одна карточка (`Источники: #12`); идентификаторы в базе сквозные, поэтому
  карточка общего слоя помечает заметки всех своих проектов. Счётчик переживает перезапуск десктопа;
- кнопка **«Обработать заметки»**: одно нажатие проходит по всем проектам порциями. Рядом — выбор одного
  проекта (с числами несведённых) и выбор модели обработки, а пока проход идёт — «Отменить», «проход 2 из 3,
  сведено 34 из 87» и счётчик времени. Отмена срабатывает между проходами: текущий дожидается модели;
- цена нажатия **до** нажатия: сколько будет проходов, сколько заметок берёт один проход и сколько
  примерно токенов уйдёт в модель;
- отчёт последнего прохода в той же карточке (сколько заметок → сколько карточек, куда легли карточки,
  токены) и ошибка там же, если проход не удался;
- состояние подключения: строка «Память в диалогах» — модель ищет и дописывает память сама или нет, и
  какая копия engram лежит в харнессе. Если подключения нет, вкладка говорит прямо, что заметки будут
  только сохраняться, а искать их модель в разговоре не сможет.

Тот же проход доступен командой `/memory-consolidate`: без аргумента — все проекты, с именем проекта —
только он, `черновик` (или `dry`) — показать вывод, ничего не записывая. Числа памяти показывает
команда `/memory-hygiene` (во вкладке их нет: там очередь и кнопка), а `/memory-cleanup` убирает из
обращения усвоенное старше `hygieneAfterDays` дней.

**Проекты и модель.** Проект — это **адрес записи**, а не режим: карточка ложится в тот же проект, что
её источники, а видимость определяет `scope`. Порция собирается по кругу — по заметке от каждого
проекта, — поэтому в одном запросе к модели видны разные проекты, а размер запроса зависит от порции,
а не от числа проектов. Модель для прохода берётся не у сессии, а из настроек DSH («Модели» — та самая «модель по умолчанию»,
которой харнесс заводит новых агентов). Вкладка не только показывает её, но и позволяет выбрать: выбор
пишется тем же полем, что и в настройках (`agentDefaultModel.saveSelection`). Если для обработки нужна
отдельная модель, её задают настройками плагина (`consolidateProvider` + `consolidateModel`) — они важнее
общего выбора.
Порядок выбора: настройки плагина → модель по умолчанию. Модель разговора здесь не участвует вовсе: вкладка и команда живут вне сессии, а «взять
модель последнего хода» — невидимый выбор, который потом нечем объяснить. Своих ключей плагин не
заводит: креденшелы разрешает адаптер DSH. Усилие рассуждений на этом вызове просим минимальное (`off`,
если адаптер его умеет): иначе рассуждения съедают предел вывода и структурного ответа не остаётся.

**Про MCP.** MCP обязателен: им модель сама ищет и пишет память, в том числе наполняет общий слой
(`global`/`personal`) — автосохранение ходов пишет только в проект. Без MCP-сервера работают правила
в промпте, подача записей в ход и автосохранение в проект, но общий слой наполнять нечем.

**Проект для записей модели.** Инструменты MCP называют проект по своему рабочему каталогу, а у сервера
памяти это каталог запуска десктопа — так в базе и заводились `launch-root`, `package`, `probe_ws`.
Поэтому: плагин на каждом ходу пишет снимок «где сейчас работаем»
(`%LOCALAPPDATA%\DSH-1C\engram-current-project.json`), а прокладка MCP **читает снимок на каждый вызов
записи** и подставляет проект в `mem_save` (`mem_save_prompt`) — переменная окружения для этого не
годится: она ставится один раз при запуске сервера, а человек за сессию успевает переключиться в другую
рабочую область. Уже названный проект прокладка не перебивает, поиск и подача памяти проектом не
сужаются (`mem_search`, `mem_context` видят всю базу). Явная настройка `project` в конфиге MCP
(`engram-mcp.json`) важнее снимка.

Что делает проход:

1. берёт сырые заметки, на которые ещё не ссылается ни одна карточка, — свежие сверху, без выводов,
   без помеченных и мягко удалённых. **Сырая заметка — всё, что не карточка**: и хроника ходов
   (`discovery`), и любой другой тип, каким его назвал `captureType` или модель через инструменты.
   Карточками считаются только `pattern`, `decision`, `architecture` — этот список закрыт, поэтому
   смена типа автосохранения не выкидывает заметки из обработки. Заметки идут по кругу от каждого
   проекта, порция ограничена числом (`consolidateNotes`) и знаками (`consolidateInputChars`);
2. отдаёт порцию модели харнесса: собственных ключей у плагина нет;
3. получает 1–3 карточки-вывода со структурой `What / Why / Where / Learned`;
4. проверяет слой и адрес карточки сам, а не на слово: `global`/`personal` принимается, только если
   источники лежат **в двух разных проектах** (иначе карточка понижается до проектной — так общий слой
   остаётся правилами, а не свалкой выводов). Проектная карточка пишется в проект своих источников по
   большинству, чужие ссылки из неё убираются: карточка про один проект не должна помечать заметки
   другого;
5. записывает карточки через engram тем же путём, что и автосохранение, и **дописывает ссылки на
   источники** — `Источники: #12, #15` ставит плагин по идентификаторам, которые вернула модель,
   а не модель по памяти;
6. если в очереди остались заметки, а проходов сделано меньше предела (`consolidateMaxPasses`, по
   умолчанию 3), берёт следующую порцию. Проход, не давший ни одной карточки, останавливает цикл:
   заметки без вывода иначе ходили бы по кругу;
7. показывает отчёт: сколько заметок → сколько карточек, куда легли карточки, сколько токенов ушло
   и почему обработка остановилась, если остановилась.

`черновик` — это один проход без записи: показать, что получилось, не платя за все три.

Сырые заметки не удаляются и не правятся: вывод ложится рядом с ними. Если карточка ошибочна, её
снимают одной правкой, а источник остаётся на месте — точность терять не на чем.

Проход не привязан к разговору: собирает и пишет всё сам, у сессии не берёт ничего. Поэтому тот же
проход сможет запускать крон — отдельным плагином и без правок здесь.

## Гигиена памяти

Память портится не от нехватки места, а от устаревших и дублирующихся записей: система через
полгода уверенно отвечает «всё ещё Postgres» — через шесть недель после переезда на MySQL.
Практика сходится на четырёх рычагах — **importance** (что вообще становится записью),
**merge** (новое вытесняет старое), **decay** (старое слабеет), **eviction** (когда запись уходит
совсем) — и на одном выводе: **вытеснять, а не удалять**; жёсткое удаление нужно для секретов и
требований закона, а не для «чистоты» ([Hindsight/Vectorize, разбор четырёх рычагов](https://hindsight.vectorize.io/blog/2026/05/21/agent-memory-consolidation),
[Oracle: четыре операции памяти и забывание](https://blogs.oracle.com/developers/agent-memory-why-your-ai-has-amnesia-and-how-to-fix-it),
[дизайн-гайд по TTL и устареванию](https://hidekazu-konishi.com/entry/ai_agent_memory_design_guide.html)).

| Рычаг | Что советует практика | Что есть у нас |
| --- | --- | --- |
| importance | высокий порог на входе: запись — только про завершённую работу или вывод | триггер автосохранения («сделал» или «выяснил» + содержательный итог) и правило «не больше двух записей на задачу» |
| merge | новый факт вытесняет старый, а не ложится рядом | тема (`topic_key`): запись о той же работе **обновляется** (`revision_count`), `mem_update` правит содержание, заголовок и уровень, `personal`/`global` принимают поднятые правила |
| decay | старое слабеет: устаревание по времени и по подтверждению, а не по факту повторного чтения | порядок отбора по-прежнему лексический (веса свежести нет), но устаревшее перестаёт участвовать в обработке: усвоенное видно по ссылкам и убирается из обращения вместе со своими дублями |
| eviction | мягкое удаление по умолчанию, жёсткое — только по требованию | `deleted_at` (мягкое) — так расходится всё, что убирается, в том числе командой `/memory-cleanup`; `engram delete --hard` — только вручную и осознанно |

Что плагин делает сам, без модели:

- **`/memory-hygiene`** — отчёт о состоянии базы: сколько заметок сведено в выводы, сколько ждёт
  сведения, что уже убрано из поиска, сколько дублей и связей между записями. Считается из базы
  (`duplicate_count`, `memory_relations`, ссылки «Источники:» в карточках);
- **`/memory-cleanup`** — убирает из обращения заметки, у которых уже есть вывод-карточка, и только
  старше `hygieneAfterDays` дней. Это `engram delete` без `--hard`: строка остаётся в базе вместе с
  текстом и провенансом, из поиска и очереди она уходит. **Плагин не удаляет ничего сам** — уборку
  зовёт человек.

Во вкладке «Память Engram» этих чисел нет намеренно: человеку там нужны очередь и кнопка, а не «связи ждут
разбора». Термины гигиены остаются в командной строке — там их читает тот, кто за ними пришёл.

Что уборка **не** заберёт никогда: заметку без вывода (иначе знание пропадёт вместе с ней), заметку
в общем слое (`personal`/`global` — это вынесенные правила, а не хроника) и помеченную вручную
(`mem_pin`: «это должно пережить чистку»). Проверки этого — в `test/hygiene.smoke.mjs`.

Что для этого уже есть в самом engram (проверено на 2.0.0 и 2.1.0):

- мягкое удаление `engram delete <id>` и жёсткое `--hard`, каскад по проекту `delete project <name>`;
- `mem_pin` / `mem_unpin` — правило, которое обязано переживать чистку (и в правилах плагина
  модели сказано помечать так то, что должно остаться);
- `engram conflicts list|stats|scan` — противоречащие записи; семантический разбор зовёт LLM,
  поэтому по умолчанию он не включается;
- `engram projects consolidate` — слить похожие имена проектов, `projects prune` — убрать пустые;
- `engram stats`, `engram timeline`, `engram export`/`import` — увидеть, что накопилось, и вынести наружу;
- `mem_review`, `mem_judge` — разбор качества и противоречий самой моделью.

Порядок уборки, когда накопилось сверх того, что делает плагин (всё, кроме последнего шага,
безопасно и обратимо):

1. `engram projects consolidate --dry-run` — увидеть, не разъехались ли имена проектов;
2. `engram stats --all` и `engram conflicts scan --dry-run` — объём и противоречия;
3. `engram delete <id>` — мягко убрать устаревшее (секреты — `--hard`);
4. правила и выводы, которые должны остаться, — `mem_pin`, чтобы чистка их не забрала.

## Границы

- `node:sqlite` в Node 22/24 помечен экспериментальным и печатает `ExperimentalWarning` в лог — поведение от версии к версии не обещано;
- субагенты инъекцию не получают намеренно: у них своя задача и свой контекст;
- проект определяется по рабочему каталогу хода, поэтому запись, сохранённая из другого каталога, найдётся только при совпадении имени проекта;
- автосохранение пишет через CLI engram: если бинарник не найден, оно один раз сообщает об этом в лог и выключается, ход не ломается;
- автосохранение ставит CLI те же переменные, что и шим MCP: свой каталог данных и `ENGRAM_NO_UPDATE_CHECK=1` — иначе каждый запуск бинарника стучит в GitHub за версией;
- правила живут в секции системного промпта, поэтому плагин объявляет `inject: ['systemPrompt']`: без этого объявления `ctx.systemPrompt` не существует, секция не регистрируется, и ошибки тоже нет — правила просто молча не доезжают.

## Проверка

```bash
npm test    # восемь наборов
node test/store.smoke.mjs        # поиск, бюджет, промахи
node test/hook.smoke.mjs         # pre-step, общий слой, правила в промпте, автосохранение, отказы, вкладка и команда
node test/capture.smoke.mjs      # разбор хода: когда запись нужна, а когда нет
node test/mcp-setup.smoke.mjs    # самодостаточность пакета: раскладка половины, объявление сервера, идемпотентность
node test/consolidate.smoke.mjs  # обработка заметок: порции по проектам, слои, предохранители, отчёты
node test/panel.smoke.mjs        # статистика и состояние прохода на вкладке
node test/client.smoke.mjs       # клиентская половина без браузера: подписи, числа, блокировки
```

`store` прогоняет 19 запросов (точная форма, падежи, словообразование, множественное число,
синонимы, идентификаторы, регистр) на 10 записях — recall@1 19/19 и на синтетической базе со
схемой engram, и на настоящей базе, собранной CLI engram, ~0,3 мс на запрос. `hook` проверяет
инъекцию, правила и запись на поддельном `ctx`: сообщение встаёт перед репликой пользователя,
повтор не инжектится, общая запись получает место в бюджете, чужой проект не утекает,
автосохранение доходит до базы через настоящий engram, `dispose` освобождает стор. `capture` —
разбор хода и заголовок. `mcp-setup` — раскладка MCP-половины и объявление сервера на временных
каталогах: повторный проход ничего не копирует и ничего не переписывает, чужую настройку сервера
не трогает. `consolidate` — порция по кругу от разных проектов, цена нажатия, правило общего слоя,
остановки (пустая порция, отмена, предел проходов, черновик) без сети и без настоящего engram:
запись подменяется функцией, которая кладёт строку в фикстуру так же, как это делает engram.
`panel` — счёт по базе, сквозной учёт сведённого и состояние прохода. `client` — клиентская
половина на подделанном загрузчике модулей: подписи, числа, блокировка кнопки, отчёт из нескольких
строк.

Тесты не касаются рабочей установки: каталог харнесса уводится во временный. Если рядом нет
бинарника engram, проверки на настоящем бинарнике пропускаются — задайте `ENGRAM_BINARY`.
