# Редакционная политика

Как выпускается версия плагина, что проверяется каждый раз и чего в репозитории быть не должно.

## Что считается выпуском

1. Версия плагина в `package.json` — по смыслу: правка текстов, сообщений и мелких дефектов даёт
   патч (`0.1.0` → `0.1.1`), новая возможность — минор (`0.1.1` → `0.2.0`).
2. Версия engram в поставке — `mcp/VERSION` (число без `v`) и запись в `mcp/VENDOR.md` с хешем.
3. Собранный архив `dsh-engram-memory-<версия>.tgz`, поставленный в десктоп.
4. Коммит выпуска и тег с тем же номером без буквы `v` (`0.1.1`).

Версия плагина и версия engram живут отдельно: первая — про сам плагин, вторая — про то, что внутри.
Плагин может обновиться, а engram остаться прежним, и наоборот.

## Порядок выпуска

**1. Проверить апстрим engram — всегда, даже если в `mcp/` ничего не менялось.**

```bash
gh release list --repo Gentleman-Programming/engram --limit 3
```

Сравнить верхний релиз с тем, что стоит в `mcp/VERSION`. Если наверху новее — либо обновляем в этом
же выпуске, либо прямо в описании выпуска пишем, что остались на прежней версии и почему.

**2. Обновление engram (если решили обновлять).**

- скачать из релиза `engram_<версия>_windows_amd64.zip` и `checksums.txt`;
- сверить SHA-256 архива со строкой в `checksums.txt` — сверяем с опубликованным файлом, а не с тем,
  что показывает загрузчик;
- распаковать и взять только `engram.exe`: остальное в архиве относится к облачной синхронизации, её в
  поставке нет;
- посчитать SHA-256 самого `engram.exe` и записать в `mcp/VENDOR.md` вместе с версией и датой; прежнюю
  версию оставить строкой «предыдущая» — чтобы было видно, с чего перешли;
- обновить `mcp/VERSION`.

**3. Прогнать проверки.**

```bash
npm test
```

Восемь наборов, все зелёные. Если проверки идут на настоящем engram, он берётся из пакета или из
`ENGRAM_EXE`: после смены версии прогон на настоящем файле обязателен.

**4. Собрать и поставить в десктоп.**

```bash
npm pack
node "D:/DSH/local-plugins/dsh-desktop-install.mjs" dsh-engram-memory-<версия>.tgz dsh-engram-memory
```

**5. Перезапустить десктоп и посмотреть вкладку «Память Engram».** Очередь считается, обработка
запускается, внизу — версия engram из `mcp/VERSION`. Если внизу старая версия, значит хост-часть не
подхватилась: десктоп надо закрыть и открыть заново.

**6. Обновить документацию**, если выпуск меняет то, что в ней написано: `README.md` (как выглядит
вкладка, что видно в отчёте), `docs/reference.md` (числа настроек), `mcp/VENDOR.md` (версия и хеши).

**7. Коммит и тег.**

```bash
git commit -am "<версия>: что изменилось"
git tag <версия>
```

**8. Если плагин уходит в сборку «DSH для 1С»** — в том репозитории пересобрать каталог компонентов:
`node scripts/prepare-installer-catalog.mjs`. Без этого шага в сборке останутся прежний плагин и
прежний engram, хотя в этом репозитории всё уже обновлено.

**9. Пуш** — только когда всё выше пройдено: `git push` и `git push --tags`.

## Чего в репозитории быть не должно

- названий объектов и файлов заказчика, имён их конфигураций, номеров и текстов задач: примеры в
  документации только обезличенные;
- путей вида `C:\Users\<кто-то>` в текстах и объяснениях (пути установки в командах — можно: они не про
  человека);
- ключей, токенов, адресов внутренних сервисов, выписок из переписки;
- дампов и журналов памяти (`.engram`), собранных архивов `.tgz`, скачанных архивов апстрима `.zip`,
  каталогов зависимостей — они перечислены в `.gitignore`.

Правило простое: если строку неловко показать постороннему — в репозиторий она не идёт.

## Короткая проверка перед пушем

- `npm test` зелёный, прогон на настоящем engram сделан;
- версия апстрима engram проверена, и её значение видно в `mcp/VERSION`;
- в диффе нет персоналки и ключей: `git diff --staged | grep -iE "АВТ_|token|secret|C:\\\\Users"`;
- `mcp/VENDOR.md` и `mcp/VERSION` не разошлись с тем, что реально лежит в `mcp/engram.exe`.
